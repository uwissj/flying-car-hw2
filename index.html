SHEET 00 / INDEX / 标题栏

把驾驶员拿掉之后，安全去了哪里

INDEX / 标题栏
FUNDAMENTALS OF FLYING VEHICLE TECHNOLOGY · COURSEWORK 02 · DRAWING 00

安全不再只是产品属性，而是体系属性

有人驾驶飞机有一道最后的、不在图纸上的冗余：驾驶员。EH216-S 把这道冗余拿掉了。于是「这架飞机安不安全」这个问题，变成了「这套运行体系能不能在没有人现场判断的情况下持续安全」。我这份分析不沿用失效概率分解的老路，改从运行概念、特定运行风险评估、符合性证据与体系兜底四条线拆。

核心论点 / THESISTC 审的是设计，AC 审的是单机，PC 审的是生产，OC 审的是组织。四证齐全只说明「每一段都被审过」，不说明「风险被消除」——它只是从机上被搬到了链路、地面站、运营人和规章里。

因此本作业的分析对象是大系统：航空器 + C2 链路 + 地面指挥中心 + 运营人 + 空域 + 审定规章。任何只画飞机本身的故障分析，都会漏掉最要紧的那几层。

SHEET 01 / CONOPS / 运行概念

先划责任边界：谁在回路里

CONOPS / 运行概念

01.1「远程接管」不是「远程驾驶」

公开资料写的是：指挥控制中心集成监控、调度、预警，与航空器实时数据交换，并在应急时干预。这里的关键词是监控与干预，不是实时杆操纵。地面操作员不具备飞行员那种连续的、手眼闭环的操纵能力。

这个措辞差别决定了整套安全论证：不能再假设「人会在最后一刻把飞机拉回来」。所有关键决策必须在机上自主完成，地面侧只提供监控、调度与有限干预。

表 01-1 · 安全责任矩阵（作者整理）
功能机上地面 / 运营人局方
稳定与导航飞控自主监控审定
航线与放行执行预置申请 / 放行批准空域
失效检测表决 + 自检告警复核符合性要求
应急决策自主迫降干预 / 通报运行规范
乘客疏散图示自解释地面人员应急程序审查
持续安全数据记录事件上报 / 维护监督
作者判断表里最值得盯的是「应急决策」那一行：决策主体在机上，但后果由地面运营人和公众承担。责任与能力不重合，正是这类系统最难写清楚的地方。
SHEET 02 / SORA / 特定运行风险评估

SORA：从运行场景反推安全措施

SORA / 特定运行风险评估

02.1为什么换一套方法

按 ARP4761 那套，从功能失效状态出发、给定量概率目标，适合有人运输类飞机。但对无人驾驶载客，最迫切的问题不是「某个部件失效概率是多少」，而是「这一次运行在什么环境里、对地面和空中的第三方造成什么风险」。

SORA 的顺序正好反过来：先定义运行概念（ConOps），再评地面风险 GRC 与空中风险 ARC，经过缓解措施后确定 SAIL（特定运行保证与完整性等级），最后导出一组 OSO（运行安全目标）。

对 EH216-S 来说，「预设航线 + 限定区域 + 起降点清空」本身就是最强的风险缓解措施，重要性不低于任何硬件冗余。

说明下面的面板是按 SORA 思路做的教学化简化整理，不是官方审定结论，也不代表该型号的实际运行批准范围。

02.2场景 → 措施（可切换）

02.3从场景对比里读出来的结论

把四个场景并排看，风险等级并不主要由飞机决定，而由地面人口密度和空域混合程度决定。同一台 EH216-S，在景区水域上空和在城市建成区上方，几乎是两个不同的产品。这也是为什么「城市通勤」在 25 min / 30 km 的包线和高密度空域下，现阶段不成立——不是飞机不够好，是运行条件还没被建立。

SHEET 03 / MOC / 审定证据

符合性验证：证据是怎么被造出来的

MOC / 审定证据

03.1没有现成规章可套

2022 年 2 月，民航局为这个型号单独颁布《EH216-S 型无人驾驶航空器系统专用条件》。这句话的分量在于：审定时连「按什么标准审」都是新写的。安全基线不是从既有条款里查出来的，是边审边定义出来的。

因此「符合性」在这里不是填表，而是要用一套方法把「设计满足了某条要求」证明给审查方看。

表 03-1 · 常用符合性方法（教学化整理，非条款原文）
代号方法适用
MC0符合性声明 / 说明条款本身可由设计说明直接覆盖
MC1设计图纸与计算结构强度、载荷、包线
MC2分析 / 仿真飞控逻辑、失效重构
MC3安全性评估失效影响、共因分析
MC4实验室试验静力、落震、螺旋桨
MC5地面 / 机上检查装配、制造符合性
MC6飞行试验最终型号合格审定试飞
MC7–9模拟器 / 设备鉴定 / 其他按条款选用

03.2数字能证明什么，不能证明什么

官方披露：1000+ 天、500+ 摸底试验、40 000+ 飞行架次、65 大项审查实验、450+ 正式符合性验证科目。这些证据的强度在于覆盖面与可追溯——每一条要求都能对应到一种证明方法。

作者判断但证据数量不等于风险穷尽。专用条件是为一个具体型号、在具体运行设想下写就的；当运行场景从景区扩展到城区、从白天扩展到夜航，原来的符合性矩阵需要重新打开。四证证明的是「按当时的约定证明过了」，不是「证明完了」。
SHEET 04 / ARCH / 系统兜底

没有驾驶员兜底：冗余必须自己闭环

ARCH / 系统兜底

04.1机上必须自己做完四件事

检测 → 决策 → 执行 → 着陆，全程没有现场人为判断。公开资料提到的「全备份关键部件、多套飞控表决、内置故障安全系统自主判断继续飞或安全迫降」，正是为这四步准备的。

表 04-1 · 冗余层与残余问题
层次措施残余问题
部件关键飞行部件全备份备份是否物理隔离
系统多套飞控 + 表决 + 传感器同版软件 / 共电源导致共因
动力8 轴 16 旋翼，单桨失效可重构相邻多轴失效的配平边界
能源智能电池管理热失控蔓延、低温与老化
决策fail-safe 自主迫降可选迫降点是否始终可达

04.2「返航」不如「迫降」现实

25 min 续航、30 km 设计航程意味着留给处置的时间窗口非常窄。有人机可以靠驾驶员盘旋、等待、选场；这里必须预先在航线沿线布好备降点，并把「哪里能落」写进飞行计划，而不是出事后临时找。

换句话说，应急能力主要不是机上能力，是航线规划能力。这又回到了体系。

共因提醒上面每一层冗余都默认「电还在、链路还在、地面站还在」。电源与链路是跨层共因，任何一层的冗余度都会被它们同时打折；这也是我认为最该做共因分析的位置。

04.3和按功能分解的老方法比

如果按功能危害分析逐项列失效状态，会得到一个很整齐的表格，但容易把「体系没接住」这类风险漏掉。我改用时序图，是想把「时间不够」这个约束摆到台面上——它不是某个部件的失效，却是很多失效最终变严重的原因。

SHEET 05 / C2 / 信息与运行

链路、地面站与网络安全

C2 / 信息与运行

05.1链路既是神经，又不能是依赖

官方强调加密通信与单机独立密钥、机队集中调度。但这里有一对必须同时成立、又很难同时验证的要求：

① 链路是地面监控、调度与应急干预的通道，属于运行体系的一部分；
② 链路中断时，航空器仍须自主完成飞行或安全迫降，不能「等地面指令」。

对有人机，通信中断后飞行员照飞；对无人驾驶，通信中断必须触发一套预设的自主行为。这条边界如果没验证透，冗余设计再漂亮也没有落点。

表 05-1 · 信息与运行侧威胁清单
威胁后果控制思路
C2 链路中断 / 降级失去监控与干预失联预设模式、不依赖地面的关键决策
GNSS 欺骗 / 干扰位置 belief 错误惯导 / 视觉 / 地标备份定位
地面站被入侵或误操作机队级错误指令权限分级、双人复核、指令白名单
机队调度冲突多机间隔不足集中调度 + 电子围栏 + 航线隔离
软件版本 / 配置不一致同型机行为分叉构型管理与批次追溯
飞行数据被篡改或缺失事件无法复盘机载记录 + 独立留存

05.2OC 审的是组织，不是设备

2025 年 3 月首批 OC 发给运营航司，审核覆盖运营主体、组织架构、运营制度、运行环境与安全性能。这句话值得读两遍：拿到 OC 的是公司，不是飞机。

因此人员资质、值班制度、维护间隔、事件上报、演练频率，都是安全系统的一部分；设备再冗余，组织失灵一样会出事。

作者判断这类产品最容易被低估的风险是「流程性共因」：同一个地面站、同一套排班、同一版运行手册，会同时影响它监控的所有飞机。硬件冗余解决不了这个。

05.3乘客看不见的那一层

乘客接触到的是舱门和座椅，接触到安全体系的地方其实只有登机前的安全简报。信息设计的缺口就在这里：把一套复杂的运行体系，压缩成两分钟内能理解、且不引起误解的说明。

SHEET 06 / 3RD PARTY / 外部风险

第三方风险与公众接受度

3RD PARTY / 外部风险

06.1风险主要发生在地面

景区和营地多为开放场地，围观者、儿童、车辆可能进入下洗流与桨盘范围。16 个桨盘带来的声源与下洗是分散的，安全半径要按最大风速漂移量而不是按机身尺寸定。

表 06-1 · 第三方风险与控制
风险源控制
围观者 / 儿童误入物理围栏 + 清空检测 + 声光预警 + 双人放行
车辆与硬质地面起降区铺装与隔离、迫降点预先勘选
侧风 / 能见度突变气象门限硬性放行条件，不作「建议」
噪声与振动投诉运行时段限制、社区沟通、实测数据公开
落地后起火 / 侧翻纯机械应急手柄、舱内外双操作点

06.2无人驾驶会放大舆论后果

同等程度的事故，发生在「没有驾驶员的载人飞行器」上，公众对品类的信任损失会明显更大。原因不是技术，是心理契约：乘客交出的不是对一名司机的信任，而是对一套看不见的体系的信任。一次事故会被读成「体系不可信」，而不只是「这一架出了故障」。

作者判断所以公众沟通不是运营之外的软工作，而是安全体系的一环：把运行边界（哪里能飞、什么天气不飞、失联会怎样）讲清楚，比宣传「零事故」更能建立可持续的接受度。
SHEET 07 / CONCLUSION / 建议

结论：把风险放回体系里

CONCLUSION / 建议

做完这一遍，我对「四证齐全」的理解变了。它不是终点，而是一张清单：设计、单机、生产、组织，各自被审过一遍。真正决定安全的，是这四段之间的接缝有没有人负责。

07.1分层的改进建议

表 07-1 · 八条建议
层面建议
设计端把「链路中断」当作顶层工况而不是异常分支，验证全部关键决策可在无地面指令下完成
设计端电源、链路、地面站做跨层共因分析，明确冗余度被打折后的残余能力
运行端每条航线预先勘选备降点，并把可达性写进飞行计划与放行条件
运行端地面站告警分级与接管权限做独立人因验证，避免一人多机时的告警淹没
组织端把值班、排班、维护、事件上报纳入同一个安全绩效闭环，防止流程性共因
组织端运行场景扩展（城区、夜航、复杂气象）时重新打开符合性矩阵，不沿用原结论
规章端把「地面指挥中心」与「C2 链路」作为独立审定对象写进要求，而非视为附属设备
公众端公开运行边界与实测噪声 / 事件数据，用可核对的信息替代零事故话术

07.2回到我自己的专业

这份分析对我最有用的地方，是让我看清「界面」的范围被放大了。以前做座舱，界面是仪表和门把手；现在做无人驾驶载客，界面还包括登机前的两分钟说明、地面监控屏的告警优先级、起降点的围栏和地面指示。

这些东西不在飞机上，却直接决定乘客和第三方是否安全。工程负责让失效不发生，设计负责让体系的边界被人看懂——看不懂的边界，等于没有边界。

与作业一的关系作业一得出的结论是「工业设计的主战场从座舱移到了体系」；这份安全分析从另一侧印证了同一件事：风险也从机体移到了体系。两条线在这一点上合拢。
